# Phase 5 — PeerTube Integration Plan

> Status is updated as each subphase is implemented and verified. Nothing is
> marked verified unless the command or live request was actually executed.

## 5.1 Repository inspection and API feasibility — DONE

Existing architecture inspected:

- Clean Architecture layers: `domain`, `infrastructure`, `application`, `presentation`.
- BLoC + GetIt + Injectable, generated by `build_runner`.
- Playback: single `GlobalPlayerController` (media_kit `Player` + `VideoController`).
  Existing service players reuse `GenericPlayerControlsOverlay`.
- Navigation: `MainNavigation` bottom tabs, Home app bar opens Search/Settings with
  `MaterialPageRoute`. PeerTube will be an independent source opened from Home,
  not a replacement for any YouTube backend.
- Persistence: settings live in Drift-backed `SettingsService`. PeerTube instance
  selection is kept in a small dedicated JSON file so no schema migration and no
  existing settings/user data is touched.

Live PeerTube API checks against `https://framatube.org` (2026-11-11):

| Request | Result |
|---|---|
| `GET /api/v1/config` | `200`, instance name/version/description returned |
| `GET /api/v1/videos?start=0&count=2&sort=-publishedAt&nsfw=false` | `200`, paged `{total,data}` |
| `GET /api/v1/search/videos?search=nature&start=0&count=1` | `200`, paged `{total,data}` |
| `GET /api/v1/videos/{uuid}` | `200`, `files` + `streamingPlaylists` with HLS `playlistUrl` |
| `GET /api/v1/video-channels/{handle}` and `/videos` | documented official routes |

Confirmed shape: anonymous access works; thumbnails/avatars are returned as
`/lazy-static/...` paths that must be resolved against the instance origin.
HLS files also expose `playlistUrl` per resolution, which gives manual quality
selection without transcoding or scraping.

## 5.2 Models, API service and repository — PLANNED

- `domain/peertube/models/peertube_models.dart`
- `domain/peertube/peertube_api.dart` (contract)
- `domain/peertube/peertube_repository.dart` (contract)
- `domain/peertube/peertube_instance_store.dart` (contract)
- `infrastructure/peertube/peertube_api_impl.dart`
- `infrastructure/peertube/peertube_repository_impl.dart`
- `infrastructure/peertube/peertube_instance_store_impl.dart`

Rules: only official REST endpoints; normalize/validate instance URLs; resolve
relative media URLs; map 401/403/404/429/timeouts to `MainFailure`; never log in.

## 5.3 Discovery, search and channels — PLANNED

- `PeerTubeBloc`: instance bootstrap, config fetch, recent/trending feed,
  search, sort, pagination with stale-request protection.
- `PeerTubeChannelBloc`: channel metadata and paginated channel videos.
- UI: dedicated PeerTube browse screen with instance switcher, source badge,
  sort selector, search field, empty/error/retry states, infinite scroll.

## 5.4 Video details and playback — PLANNED

- `PeerTubeWatchBloc`: details fetch, deleted/private handling.
- Playback source builder: HLS per-quality `playlistUrl` first, direct muxed MP4
  fallback, live master playlist; no audio-only entries.
- Player: reuse `GlobalPlayerController` + `Video` + `GenericPlayerControlsOverlay`.
  Quality changes reopen the selected source and preserve position.
- Do not claim device playback verification; only stream URL reachability and
  compile checks can be performed in this environment.

## 5.5 Instance management and UI integration — PLANNED

- Instance add/remove/switch sheet with validation through `/api/v1/config`.
- JSON persistence in application support storage.
- Home app bar PeerTube entry using existing navigation conventions.
- PeerTube source labels on cards/details; responsive card layout.

## 5.6 Testing, regression and documentation — PLANNED

- Unit tests for URL validation, JSON parsing, paging and playback source
  ordering/fallback.
- `flutter analyze`, `flutter test`, `build_runner` when DI changes.
- Android Kotlin compile is not part of PeerTube (no native changes) but the
  existing Phase 4 Kotlin work remains unverified if Gradle cannot finish.
- Update `PHASE_PLAN.md` and `VYPLAY_PROGRESS.md` with exact results/limits.

## Known constraints

- No Android device/emulator: real decoding, HLS playback, PiP and notification
  behaviour remain UNVERIFIED.
- Public instances may disable anonymous listing, return 403/429, or be offline;
  those are handled as errors, not as fake success.
- OAuth/account features are intentionally not implemented in Phase 5.
